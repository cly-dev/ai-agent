## 新增需求

### 需求:收件箱必须仅向审批人展示其待审批

系统必须提供 C 端「自动化确认」收件箱接口，返回结果必须恒定过滤为 `approverUserId = 当前用户`；禁止用户看到非自己作为审批人的审批请求。对 chat / pageAction，`approverUserId` 等于发起人（谁发起谁审批）；对 webhook，`approverUserId` 为 workflow 配置指定的审批人。

#### 场景:列出本人待审批

- **当** 用户请求收件箱列表
- **那么** 系统必须仅返回 `approverUserId` 等于该用户的 `ApprovalRequest`

#### 场景:请求他人的审批记录

- **当** 用户尝试访问 `approverUserId` 非本人的 `ApprovalRequest`
- **那么** 系统必须拒绝（返回未找到或无权限），不得泄露该记录

### 需求:收件箱列表必须以表格形式提供关键决策字段

收件箱列表必须为每条待审批返回可在表格中展示的字段，至少包含标题、来源（chat/page_action/webhook）、关联 workflow、创建时间、停留时长与状态，并提供待写参数预览（`previewBlocks` / `summary`）。

#### 场景:列表包含决策所需字段

- **当** 收件箱返回一条 `pending` 记录
- **那么** 返回项必须包含 `title`、`source`、`workflow`、`createdAt`、`status` 与写操作预览摘要

### 需求:确认与拒绝接口必须校验操作者为审批人

确认（继续执行）与拒绝（终止）接口必须校验操作者 `id === approverUserId`；非审批人的操作必须被拒绝。

#### 场景:审批人确认

- **当** 审批人对本人 `pending` 审批调用确认接口
- **那么** 系统必须触发审批恢复流程（幂等）并将状态推进为 `approved`

#### 场景:非审批人尝试确认

- **当** 非审批人对某审批调用确认或拒绝接口
- **那么** 系统必须拒绝该操作且不改变审批状态

### 需求:仅 pending 状态的审批可被确认或拒绝

系统必须禁止对非 `pending` 状态（`approved`/`rejected`/`expired`/`cancelled`）的审批执行确认或拒绝操作。

#### 场景:对已处理审批再次操作

- **当** 用户对一条已 `approved` 或 `rejected` 的审批调用确认/拒绝
- **那么** 系统必须拒绝该操作并提示该审批已处理
